# Coding standards and service conventions (ARC-09)

Applies to every service. Detailed API conventions live in [07-api-conventions](03-architecture/detailed-design/07-api-conventions.md); this document collects the remaining rules so developers do not have to guess.

## 1. Directory layout

```
services/<svc>/
  pom.xml | pyproject.toml
  Dockerfile                       # SA-owned, developers do not edit
  deploy/values-local.yaml         # developers may add non-sensitive environment variables
  src/main/java/org/shp/<svc>/
    api/            # controllers, DTOs, mappers; accept/return only contracts from contracts/openapi
    app/            # @Transactional use cases: the only place that opens a transaction, writes data + outbox.add(...)
    domain/         # models + pure business rules, no Spring/JDBC/Mongo imports
    infra/          # repositories (JdbcClient/MongoTemplate), internal REST clients, Blob
    messaging/      # event consumers, always wrapped in inbox.handleOnce(...)
    config/         # PlatformConfig (SA-owned, generated by tools/scaffold/java_service.py)
  src/main/resources/db/migration/ # Flyway (only services that use PostgreSQL)
  src/test/java/...                # same package as the code; integration tests use Testcontainers
```
This layout is generated by `tools/scaffold/java_service.py` and is the same for every Java service ([overview §4](03-architecture/overview.md#4-inside-a-java-service)).
Outbox, inbox and idempotency are already provided by `config/PlatformConfig` (the `shp-data-*` libraries); services do not rewrite them.

Python services (`ai`, `ml`): packages `src/shp_ai`, `src/shp_ml` split by feature (e.g. `assistant/`, `kb/`, `summary/`, `booking/`, `eval/` in ai;
`train.py`, `serving.py`, `drift.py`, `consumer.py` in ml); FastAPI routers in `api_*.py` or `main.py`; `src/shp_platform/` is a copy of `libs/python`
(edit in `libs/python` then run `tools/pylib/sync.py`); tests in `tests/`.

## 2. Errors
- Throw `ShpException` with a code from `ErrorCatalog` (27 codes, matching [07 §5](03-architecture/detailed-design/07-api-conventions.md)). **Do not invent new codes**: open an issue for the SA.
- `ShpExceptionHandler` turns it into a FHIR `OperationOutcome` (clinical APIs) or `application/problem+json` (other APIs). Messages have vi and en variants.
- Never return stack traces, table names, SQL statements or input values in a response. 5xx returns only a generic code and the `traceId`.

## 3. Logging, tracing, metrics
- One-line JSON logs with `traceId` and `spanId` (OTel adds them). Levels: `ERROR` needs a human, `WARN` unexpected but self-recovering, `INFO` key business events, `DEBUG` off in UAT/prod.
- **No PII in logs, events, span attributes or metric names/labels**: no names, phone numbers, emails, dates of birth, national IDs or clinical content. Log internal IDs only (`Patient/123`).
- Do not log whole request/response bodies. For validation errors, log the field name, not the value.
- Every service exposes `/actuator/health`, `/actuator/info`, `/actuator/prometheus` (`shp-service-defaults` enables them). New business endpoints get RED metrics automatically via Micrometer.
- Calling another service: propagate `traceparent`. Events: put `traceparent` in the envelope (`CloudEvents.create` does this).

## 4. Configuration
- Environment variables only (Spring: `SPRING_*` or `shp.*` in `application.yml`). Do not read config files outside the image, do not hard-code URLs, hosts or passwords.
- Secret values come only from Key Vault (CSI) in the cloud or `dev/.local/` on a dev machine. No "convenient" defaults for secrets in code.
- Toggle features with `SHP_FEATURE_<NAME>`, defaulting to off for unfinished features.

## 5. API and versioning
- Paths are `/api/v1/...`; backward-compatible changes (adding optional fields) keep `v1`; breaking changes add `v2` in parallel for at least one sprint.
- Contract first: edit `contracts/openapi` and `contracts/events` in the same PR, and `tools/contracts/check_all.sh` must be green.
- New endpoints must carry `@RequireShpAuthz` and a matching row in `contracts/authz/matrix.yaml`; otherwise the `UnprotectedEndpoints` test fails CI.
- State-changing writes accept `Idempotency-Key` (PostgreSQL: `PostgresIdempotency`; MongoDB: `MongoIdempotency`).
- Required headers ([07 §3](03-architecture/detailed-design/07-api-conventions.md#3-headers)) are checked by `shp-web` before authorization:
  - Endpoints that need `Idempotency-Key` use `@RequireIdempotencyKey` (missing -> 428); read the key with `PreconditionInterceptor.idempotencyKey(req)`.
  - Every `PUT` and any endpoint with `@RequireIfMatch` requires `If-Match: W/"<versionId>"` (missing -> 428). Compare against the current version with
    `PreconditionInterceptor.checkVersion(req, version)` (mismatch -> 412); the store still writes conditionally on the version.
  - `ETag: W/"<versionId>"` is set automatically when the body has `meta.versionId` (FHIR) or is `Versioned` (DTO).

## 6. Data and events
- Each service writes only to its own data store ([ADR-0014](03-architecture/adr/0014-database-per-service-review.md)). For another service's data: call its API or listen to events.
- Publish events in the **same transaction** as the data change via `outbox.add(...)`; wrap consumers in `inbox.handleOnce(...)` for exactly-once handling.
- Events contain only IDs and minimal fields, no PII.

## 7. Tests
- Every business class has unit tests; data access and the bus use Testcontainers (real PostgreSQL, MongoDB, RabbitMQ).
- Line coverage >= 70% (CI blocks below). Tests must be repeatable, order-independent, and make no external network calls.
- Test data comes from the synthetic data generator ([00-synthetic-data](00-synthetic-data.md)); do not invent realistic-looking data yourself.

## 8. Code style
- Java: Spotless (`mvn spotless:apply`), `-Werror`, no `@SuppressWarnings` without a documented reason. Python: `ruff` + `mypy` strict.
- Small commits; titles `<story> (<task>): <description>` per [00-git-github.md](00-git-github.md), e.g. `US-041 (NTF-02): create reminders on appointment-booked`.
